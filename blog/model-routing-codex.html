Model routing in Codex: Terra explores, Luna executes

How to reduce the main agent’s context with specialized subagents—without outsourcing architecture, security, or technical accountability.

By Levi LugatoSeptember 11, 202612 min read

A large share of a coding agent’s cost does not come from sophisticated reasoning. It comes from I/O: locating files, reading large modules, comparing manifests, counting occurrences, generating boilerplate, and running predictable checks. Putting all of that into the primary model’s context is like hiring a principal engineer to spend hours taking directory inventory.

The alternative is model routing: classify each subtask by the capability it requires and send it to the appropriate model. The primary model remains responsible for the problem; workers absorb read-intensive exploration and mechanical execution.

The goal is not to remove tokens from the system. It is to prevent low-value tokens from occupying the most expensive and cognitively important context.

The problem: the context window is an architectural concern

When an agent reads dozens of files, every result competes for space with requirements, previous decisions, test failures, and high-value evidence. Even before a hard context limit is reached, the signal-to-noise ratio deteriorates. The model must repeatedly recover what matters from an increasingly large transcript.

This makes context engineering an architectural discipline. A good prompt is not enough; we must control which data enters the context, who processes it, and the format in which it returns.

A practical division of responsibility

In Codex, I use three levels. Routing is not simply about a “strong model” and a “weak model.” It is based on the shape of the task:

OwnerWorkloadWhy
gpt-5.6-terra
low · read-only		Read-heavy scans, large files, cross-repository correlation, and document processing.Explores broad context and returns distilled evidence.
gpt-5.6-luna
low		Searches, counts, manifests, boilerplate, localized changes, and predictable validation.Executes narrow, clear, repetitive tasks quickly.
Primary agentArchitecture, complex debugging, security, conflict resolution, integration, and final conclusions.Preserves end-to-end coherence and accountability.

This separation prevents two common mistakes: using a frontier model for purely mechanical work, or allowing an economical worker to make decisions that require system-level understanding.

Fan-out, reduction, and synthesis

For a broad analysis, the primary agent can run a small map-reduce pattern:

user request
    │
    ├── broad_reader ──► topology + relevant files
    ├── mechanical_worker ──► counts + manifests + checks
    └── primary agent ──► security + architecture + final synthesis

During fan-out, independent subtasks run in parallel. During reduction, each worker returns only structured conclusions: files, line numbers, validation, and risks. The primary agent then correlates the results and directly inspects only the decisive sections.

The output contract matters. If a subagent returns long logs or complete files, the savings disappear. Its output must be deliberately small, precise, and auditable.

AGENTS.md as a control plane

The AGENTS.md file acts as a declarative policy layer. A global rule can define when to delegate, which profile to use, and which decisions must never leave the primary agent. Repository-specific files can add constraints closer to the code.

A condensed example:

## Default delegation and model routing

- Use broad_reader for repository exploration, large-file review,
  and cross-file correlation.
- Use mechanical_worker for narrow, repeatable work.
- Keep architecture, security, complex debugging, and final
  integration in the primary agent.
- Never assign overlapping files to concurrent editing agents.

This creates a readable, versionable policy independent of each task’s prompt. Instructions alone, however, should not replace technical isolation. Agent profiles complete the policy.

TOML profiles: capability and least privilege

Custom agents can define their model, reasoning effort, sandbox, and dedicated instructions. For broad exploration, a read-only profile reduces the chance that investigation produces accidental changes:

name = "broad_reader"
model = "gpt-5.6-terra"
model_reasoning_effort = "low"
sandbox_mode = "read-only"

developer_instructions = """
Correlate evidence and return concise findings with exact paths
and line numbers. Never edit files or make final decisions.
"""

The mechanical worker can receive workspace-write, provided that its scope is narrow, its files do not overlap with another worker’s, and the primary agent reviews the diff. This is a direct application of least privilege: each agent receives only the authority necessary to complete its part.

What should not be delegated

Model routing is not an excuse to fragment accountability. Some tasks depend on deep context, judgment, and the ability to evaluate indirect consequences:

  • architectural decisions and changes to system boundaries;
  • security analysis, IAM, and data exposure;
  • debugging concurrency, race conditions, and intermittent failures;
  • destructive or difficult-to-reverse migrations;
  • resolving contradictory results from different agents;
  • final review, risk-proportionate testing, and approval for delivery.

Subagents can collect evidence in these domains, but final interpretation should remain with the agent that owns the end-to-end view.

The hidden cost of delegation

Delegation has a cost too. There is orchestration latency, some repeated context, and token consumption by the worker. For small files or tasks that take only a few minutes, the overhead can exceed the savings. Routing therefore needs a threshold: delegate when there is enough volume, real parallelism, or predictable work to justify coordination.

About the 90% reduction

The figure reported by Spotify measures the reduction of tokens in the primary agent’s context under specific scenarios. The worker still consumes tokens. The economic benefit depends on delegated volume, model pricing, and summary quality.

Accountability remains with the primary agent

The best implementation of this pattern is not the one that creates the most agents. It is the one that keeps the primary context small without losing traceability. The primary agent must validate evidence, inspect consequential changes, run appropriate tests, and reject weak conclusions.

Model routing is ultimately Platform Engineering applied to agents: specialized paved paths, guardrails, isolation, and predictable interfaces that make the system more efficient—without obscuring who remains accountable for the outcome.
